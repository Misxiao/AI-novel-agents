# 本地中文网文 Agent 管理平台 PRD

## 1. 背景

中文网文创作不是单次文本生成问题，而是长期生产问题。作者需要同时管理选题、卖点、世界观、角色、卷纲、章纲、正文、修改、审稿、伏笔、数据反馈和连载节奏。传统 AI 写作工具常以聊天或单段补全为中心，难以解决长篇创作中的遗忘、设定漂移、人物串音、章节质量不稳定和多项目管理问题。

本项目要建设一个本地优先的 Web 管理平台，内置多 Agent 创作能力，让用户可以同时管理多本小说，并让每本小说拥有独立记忆和独立生产链路。

## 2. 产品目标

### 2.1 核心目标

构建一个本地运行的中文网文创作管理平台，支持用户从灵感、立项、大纲、章节生成、评审、修改到记忆更新的闭环工作流。

### 2.2 阶段目标

MVP 阶段优先完成：

1. 多小说项目管理。
2. 每本小说的独立创作资产管理。
3. 内置多 Agent 工作流，不暴露 Prompt/Skill 配置界面。
4. 章节生产闭环：章纲读取、正文生成、评审、修改、记忆更新。
5. Agent 运行记录、任务状态和输出报告可追踪。

后续阶段扩展：

1. 参考作品导入、拆书分析和写法检索。
2. 小说平台阅读数据导入与分析。
3. 追读、掉点、评论情绪与章节表现诊断。
4. 更完整的批量生产、回滚、版本对比和质量评测。

## 3. 非目标

MVP 不做以下能力：

1. 不做 Agent 配置平台。
2. 不做 Prompt/Skill 模块管理 UI。
3. 不做可视化 Agent 编排器。
4. 不做多人协作与权限系统。
5. 不强依赖云端服务。
6. 不接入真实小说平台账号登录和自动发布。
7. 不承诺一键生成完整长篇小说。

## 4. 用户画像

### 4.1 主要用户

独立中文网文作者或 AI 写作实验者，希望在本地管理多个小说项目，并使用 Agent 辅助完成规划、生成、审稿、修改和长期记忆维护。

### 4.2 次要用户

研究 AI Native 创作工作流的开发者，希望观察多 Agent 如何在长篇创作场景中协作，并逐步扩展阅读数据分析和创作质量评测。

## 5. 核心使用场景

### 5.1 创建小说项目

用户输入小说名称、题材、简要灵感、目标读者、预期体量和风格方向。系统创建独立小说 workspace，并初始化世界观、角色、纲要、记忆和任务空间。

### 5.2 灵感与立项

用户输入一个模糊想法。灵感 Agent 和立项 Agent 生成题材诊断、核心卖点、冲突、hook、premise、故事引擎和目标体量建议。

### 5.3 大纲规划

大纲 Agent 根据立项结果生成总纲、卷规划、前 10 到 20 章章纲、伏笔账本和阶段目标。用户确认后进入章节生产。

### 5.4 章节生产

生成 Agent 读取当前小说的独立记忆、章纲、角色状态、世界观约束和写法规则，生成章节正文草稿。

### 5.5 章节评审

评审 Agent 对正文进行剧情逻辑、角色一致性、设定冲突、节奏、章末拉力、AI 味和章纲覆盖度检查，形成结构化评审报告。

### 5.6 章节修改

修改 Agent 根据评审报告执行局部重写、扩写、压缩、对白增强、章末增强和去 AI 味处理，保留版本记录。

### 5.7 记忆更新

章节通过用户确认后，系统更新 canon、人物状态、章节摘要、伏笔账本、卷进度和任务历史。

### 5.8 阅读数据分析

后续版本允许导入平台阅读数据、章节追读、收藏、评论和掉点数据。数据分析 Agent 生成章节表现诊断和创作调整建议。

## 6. 功能需求

### 6.1 小说项目管理

- 系统必须支持创建、查看、编辑和归档多个小说项目。
- 每个小说必须有唯一 `novelId`。
- 每个小说必须拥有独立记忆命名空间。
- 系统必须展示小说的当前阶段、最近任务、章节进度和质量状态。

### 6.2 创作资产管理

每本小说至少包含：

- 基础信息。
- 世界观。
- 角色库。
- 总纲。
- 卷纲。
- 章纲。
- 章节正文。
- 伏笔账本。
- 风格档案。
- 评审报告。
- Agent 运行记录。

### 6.3 内置多 Agent 能力

平台必须内置以下 Agent 能力：

- 灵感 Agent。
- 立项 Agent。
- 大纲 Agent。
- 设定 Agent。
- 生成 Agent。
- 修改 Agent。
- 评审 Agent。
- 记忆更新 Agent。
- 后续数据分析 Agent。
- 总编/调度 Agent。

这些 Agent 的配置不在前端暴露。

### 6.4 LangGraph 工作流

系统必须使用 LangGraph.js 表达核心工作流。MVP 至少包含：

- `novel-intake-graph`。
- `outline-planning-graph`。
- `chapter-production-graph`。
- `chapter-review-graph`。
- `chapter-revision-graph`。
- `memory-update-graph`。

### 6.5 任务中心

- 系统必须记录每次 Agent 任务的输入、输出、状态、开始时间、结束时间、错误信息和关联小说。
- 系统必须支持查看任务历史。
- 系统必须支持失败任务的重试入口。
- 系统应该支持通过 SSE 或 WebSocket 推送任务进度。

### 6.6 独立记忆

每本小说的记忆必须包含：

- Canon Memory：已确认事实。
- Working Memory：当前卷、当前章、近期剧情摘要。
- Style Memory：文风、禁用表达、角色口吻。
- Planning Memory：总纲、卷纲、章纲、伏笔。
- Reader/Data Memory：后续导入的阅读数据。
- Run Memory：Agent 运行记录。

任何检索和生成必须携带 `novelId` 约束。

### 6.7 用户界面

MVP 页面至少包括：

- 小说列表。
- 小说概览。
- 创作资产页。
- 大纲页。
- 章节编辑页。
- 任务中心。
- 评审报告页。

前端不提供 Agent 配置、Prompt 管理和 Skill 管理页面。

## 7. 非功能需求

### 7.1 本地优先

系统默认在本地运行。用户的小说正文、参考资料和生成记录默认保存在本地。

### 7.2 可追踪

所有 Agent 运行必须可追踪，至少保存任务输入摘要、输出摘要、使用的工作流、关联实体和错误信息。

### 7.3 可恢复

长任务失败后必须保留失败状态和上下文，允许用户查看原因并重试。

### 7.4 可扩展

架构必须允许后续接入：

- 多模型供应商。
- 本地模型。
- 向量数据库。
- 阅读数据导入。
- 批量章节生产。
- 更复杂的质量评测。

### 7.5 数据隔离

跨小说数据不得默认共享。全局写法规则和题材模板可以被多个小说使用，但小说正文、设定、记忆和任务记录必须隔离。

## 8. 成功指标

MVP 验收指标：

1. 用户可以创建至少 3 本小说并独立管理。
2. 每本小说可独立维护基础设定、角色、世界观、章纲和章节。
3. 系统可以完成单章生产闭环：生成、评审、修改、确认、记忆更新。
4. 任一 Agent 任务均可在任务中心查看状态和结果。
5. 不同小说之间不会发生记忆串用。
6. 前端不出现 Agent 配置、Prompt 管理或 Skill 管理入口。

## 9. 集成边界

### 9.1 触达系统

| 系统 | 触达方式 | MVP 状态 |
| --- | --- | --- |
| Web 管理平台 | Vite + React | 新建 |
| API 服务 | Fastify | 新建 |
| Agent 编排 | LangGraph.js | 新建 |
| 本地数据库 | SQLite | 新建 |
| LLM 供应商 | OpenAI-compatible 抽象层 | 预留 |
| 小说平台阅读数据 | CSV/API 导入 | 后续 |

### 9.2 新建边界

- Web 到 API 的 HTTP 边界。
- API 到任务运行器的任务边界。
- 任务运行器到 LangGraph 的 Agent 边界。
- Agent 到记忆系统的检索与写入边界。
- Agent 到 LLM 供应商的模型调用边界。

### 9.3 配置依赖

MVP 预期配置：

- 数据库路径。
- LLM Provider 基础配置。
- 本地文件存储路径。
- 任务并发限制。

这些配置不应在前端做 Agent 级编辑，只作为系统运行配置。

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 长篇生成质量不稳定 | 用户不信任系统 | 先做单章闭环和评审修改 |
| 小说记忆串用 | 破坏多项目可信度 | 所有查询强制绑定 `novelId` |
| Agent 输出不可控 | 难以调试 | 保存任务输入输出和工作流节点日志 |
| 过早做配置平台 | 产品复杂度膨胀 | Agent 能力内置，前端只暴露创作任务 |
| 阅读数据来源复杂 | 后续接入成本高 | MVP 先设计导入边界，不直接接平台账号 |

## 11. 决策日志

| 日期 | 决策 | 理由 |
| --- | --- | --- |
| 2026-05-26 | 前端采用 Vite + React | 用户明确指定，适合本地管理平台快速开发 |
| 2026-05-26 | 后端采用 Fastify | 用户明确指定，适合 Node.js API 服务 |
| 2026-05-26 | Agent 编排采用 LangGraph.js | 用户明确指定，适合有状态、多节点工作流 |
| 2026-05-26 | 不提供 Agent 配置、Prompt/Skill 管理 UI | 用户明确要求这些能力应内置在项目中 |
| 2026-05-26 | PRD 存放在 `docs/prds/` | 用户要求不放在 `.codex` 中 |

## 12. PRD 自检结果

本 PRD 基于当前对话完成一轮 gather-criticize 自检，结论如下：

- Business：已明确 MVP 聚焦多小说管理和章节生产闭环，避免过早扩张到平台发布。
- Technical：已明确 Vite + React、Fastify、LangGraph.js 和多小说记忆隔离。
- Security：已识别本地优先、数据隔离、后续平台数据导入风险；MVP 暂不做平台账号接入。
- Edge Case：已覆盖任务失败、记忆串用、多小说并行、后续阅读数据接入边界。

剩余低优先级问题：

- 具体数据库 schema 待技术设计与实现阶段细化。
- 首批 LLM Provider 优先级待实现前确认。
- 阅读数据平台清单待后续产品阶段确认。
