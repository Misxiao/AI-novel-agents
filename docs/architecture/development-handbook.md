# 开发手册

## 1. 当前阶段开发重心

接下来较长时间内，项目开发重心放在 Agent 底层能力建设上。默认只推进以下范围：

- `packages/agents`：Agent 定义、能力实现、Prompt 组织、结构化输出、中文网文专项能力。
- `packages/workflow`：项目自有 Workflow 编排、任务状态、运行记录、重试、恢复和人工确认点。
- `packages/memory`：小说独立记忆、上下文检索、canon 提取、记忆更新。
- `packages/repositories`、`packages/db`：Agent/Workflow 需要的本地资产读写接口和 SQLite 持久化。
- `packages/agent-cli`：绕开 Web/API 的本地验证入口。
- `docs`：架构、PRD、调研和开发说明。

除非用户明确要求，不要同步修改 `apps/web` 或 `apps/api`。Agent/Workflow 能力应先通过类型检查、构建、CLI 手工冒烟或临时 SQLite 验证，再单独规划 Web/API 接入。

## 2. Workflow 技术路线

本项目后续不再使用 LangGraph.js 开发核心工作流。历史文档或旧命名中的 `graph`、`*-graph` 只作为工作流名称或迁移遗留称呼，不代表继续引入 LangGraph 依赖。

后续 Workflow 统一采用项目内自有 TypeScript 编排模式：

```txt
Workflow 输入
-> repository 装配小说资产和上下文
-> Agent capability / Agent 类执行
-> 结构化输出校验
-> 评审或质量门禁
-> 必要时自动修订
-> 等待人工确认
-> 确认后写入正式资产和小说记忆
-> 记录 WorkflowTask、AgentRun、版本与错误
```

Workflow 代码应显式表达步骤、状态、失败原因和重试边界。不要新增 LangGraph 节点、checkpointer、graph runner 或可视化图编排相关代码。

## 3. Agent 开发约定

Agent 是系统内置能力，不是前端可配置项。新增或修改 Agent 能力时遵守以下规则：

1. 所有小说私有输入、输出、检索和记忆写入都必须绑定 `novelId`。
2. 正文生成、修订、重写、扩写、压缩和风格处理归入正文方向；当前代码中由 `chapter` 章节 Agent 承接。
3. 大纲相关的整书、分卷、章纲生成与修改归入 `outline` 大纲 Agent。
4. 评审 Agent 只输出结构化问题、质量分、责任模块和修订建议，不直接覆盖正文或大纲。
5. 记忆 Agent 不接收未确认草稿进入 canon。
6. `webnovelSkill` 只提供路由、模块定义、链路规则和 Prompt 上下文片段，不直接调用 LLM 或数据库。
7. LLM 输出必须先成为草案、补丁或报告，再由 Workflow 或 repository 在校验和人工确认后写入正式资产。

## 4. 开发与验证流程

按任务规模使用最小流程：

1. 小型改动直接定位、修改并验证，不创建设计文档或实施计划。
2. 中型改动只在对话中维护简短步骤，不生成一次性过程文档。
3. 大型或跨模块改动才补充架构或产品文档。

本项目后续不新增、修改或运行单元测试，不采用 TDD。验证按需选择：

1. 文档与文案：检查格式、链接、术语和重复内容。
2. TypeScript 局部修改：运行目标包类型检查。
3. 构建或导出边界修改：运行目标包构建。
4. CLI、Workflow 或 SQLite 行为修改：执行一次针对目标路径的手工冒烟验证。
5. Web/API 验证：仅在用户明确要求进入接入阶段后进行。

不要重复执行证明相同结论的检查，也不要为了验证 Agent 能力提前修改前端页面或 API 路由。

## 5. 信息收集约定

1. 先读目标文件和直接依赖，再决定是否需要架构文档。
2. 搜索必须限制关键词、目录和输出量，避免全仓大段输出。
3. 默认不读取全部 PRD、全部架构文档或完整 git diff。
4. 只有出现失败、行为不一致或边界不清时才扩大搜索范围。
5. 用户目标明确时直接实施，只在高风险歧义或破坏性操作前请求确认。

## 6. 下一阶段推荐功能边界

“确认后的章节资产与小说记忆闭环”是下一阶段 Agent 底层能力的优先目标。它不是 Web 功能，核心落点是让单章 workflow 的结果成为可持续写下一章的本地资产。

最小闭环包括：

- 当前章节 Workflow 已持久化章节草稿和任务记录；最终稿、评审报告、修订历史、质量门禁和 AgentRun 的独立结构化存储仍属于后续章节确认闭环。
- 生成完成后进入待确认状态，用户确认前不更新 canon。
- 确认后推进章节进度，并写入章节摘要、canon facts、角色状态变化、伏笔状态变化和工作记忆。
- 下一章上下文装配能读取上一章摘要、已确认事实、近邻章纲、伏笔和风格约束。
- 所有记录都可通过 `novelId`、`chapterPlanId`、`chapterNo`、`taskId` 串起来追踪。

这一步完成后，再考虑批量章节、质量趋势、回滚对比、SSE 进度或 Web/API 接入。
